# Development log

This project was built in one long session. The reasoning that mattered lived in the commit
messages, and the history was later squashed to a single commit to remove an accident: the
first push contained absolute paths with a Windows account name, and the only way to be sure
those are gone from the remote is to publish a history that never contained them.

The messages are preserved here verbatim, because most of the value in this repository is the
reasoning rather than the code.

 === mb-agent-bridge: let an AI agent see and play Mount & Blade 1.011 === Three primitives, zero dependencies (ctypes + stdlib only):    observe  screenshot()   capture the game's client area to PNG   act      click()/key()  inject input the 2008 UI actually accepts   know     read_gold()    locate the engine's variable block by AOB signature  The non-obvious part, and the reason this repo exists: the game samples the mouse once per frame, so a click whose press and release land in the same frame is invisible to it. A down/up/down/up batch in one SendInput call is silently dropped. Real gameplay clicks hold the button ~70 ms. That is what click() reproduces, and it was found by recording a human loading a save.  Verified against a live campaign: gold reads 5271 (matches the HUD), screenshots are 853x480 client-area captures, injected clicks change the frame.   === add the DSH plugin: register Mount & Blade as model tools === The Python bridge is infrastructure; this is what makes it a plugin an agent can actually play with. dsh-plugin/ registers four DSH model tools via ctx.get('tools').register(defineTool(...)):    mb_state  is the game running, pid, client rect, gold   mb_look   screenshot -> returns a path the model reads as an image   mb_click  click at screenshot coordinates   mb_key    send a virtual key  Child processes use file-backed stdio, never pipes: under the DSH sandbox a child opening an inherited named pipe fails with EPERM, so execFile with default options cannot be used for the Python bridge.  Verified against the real @deepseek-ai/dsh-tools: all four definitions compile and register.   === docs: document the DSH plugin route and its two non-obvious constraints ===   === perf: cut the control loop from ~110ms to ~15ms, and add a reflex combat layer === Measured before touching anything (853x480 client area):      mb_click   216 ms      mb_look   164 ms      python start   31 ms     inside a screenshot: find_window 0.7, client_rect 0.0, capture+encode 100.0  So the mechanics were never the bottleneck - PNG encoding was. Three fixes:    * zlib level 1 instead of 6 (~60 ms saved; nobody reads the extra bytes)   * numpy for BGRA->RGB when importable, pure-stdlib fallback otherwise   * optional integer downscale  Result: shot --scale 2 costs 15 ms and writes 226 KB instead of 110 ms / 790 KB. The smaller frame also cuts vision tokens ~3.5x, which is what actually matters, because the real bottleneck is the model's own latency, not the script's.  Adds mb_bridge fight: the 'little brain'. Screenshot -> inference -> click is seconds per decision; melee needs ~100 ms. So combat is split - this loop holds W and swings every 260 ms inside one process with no model in it, and the agent decides only whether to engage and when to disengage. That is faster than a human clicking (~300-400 ms), which is the entire point of moving it out of the loop.   === fix: two systematic input bugs found by playing the game === Both of these made clicks silently fail, and neither is visible from the code alone.  1. SendInput delivers to the FOREGROUND window. The agent's own chat window holds the    foreground, so every synthetic click was being posted to the chat UI and never reached    the game - which looks exactly like 'the game ignored the click'. click() now raises the    game window first, using AttachThreadInput because Windows refuses SetForegroundWindow    from a process that does not own the foreground.  2. The cursor must be seen AT the target for several frames BEFORE the press. Moving and    pressing inside one frame is treated as a stray click elsewhere. settle_ms (default 150)    reproduces the gap a human hand has naturally: move, then press.  Also documents the third one, which was a geometry problem rather than a code problem: the game renders 1280x720 but was running in an 853x480 client area. It CROPS rather than scales, so the right 427 px were off-screen - including the load-game button and dialogue options. That is why they looked unclickable. Locking the window to a client of 1282x722 made them visible.   === design A+B: structured state and named actions, plus the S1 mailbox test === The bottleneck is not model reasoning - it is the two ends of the loop. Observation is pixels read by a vision model (slow, ambiguous, and blind to anything the window clips). Action is SendInput at screen coordinates, which this engine's DirectInput path does not accept. Reasoning found all three of tonight's systematic bugs; the ends are what block us.  So: move both ends into text, and let the game execute the actions itself through its own script API - no Windows input stack involved at all.    docs/structured-state-and-named-actions.md   the design, opcode table, safety analysis   tools/verify_mailbox.py                      the S1 acceptance test  Transport is shared memory in the engine's global-variable array, because module scripts have no file or network access. Adding new variables does NOT work - the array ends around index 248 and 499+ lands in unrelated structures - so the design reuses existing dead slots (quest-scoped globals whose quest is not active).  S1 is deliberately the smallest possible experiment: one hand-written trigger that does val_add(global[480], 1) every frame. It tests the single precondition everything else depends on - that the engine executes text we wrote - and it tests nothing else, so a failure is unambiguous.  Also records the seven traps from tonight, including the two that cost the most time: the window extended under the taskbar (so clicks hit the taskbar while screenshots, which capture the window DC, showed the content fine), and Space is the campaign map's pause key (pressing it to 'advance a dialogue' silently paused the game).   === research: vendor the original save-editor sources and WarBender's format model === Instead of re-deriving the save format by hand, vendor the code that already does it:    third_party/mb-savedata-editor/   zhangriyueming/mb-savedata-editor (MIT, 100k+ downloads)                                     the original Mount&Blade savegame editor, C++ sources   third_party/.../WarBender*.cs     int19h/WarBender save-game record model (Warband)  Immediate finding from MainWnd.cpp - the game's supported display modes are listed as 800x600 through 1280x800. We had forced display_height = 720, which is not one of them, and the UI layout is evidently authored against a taller canvas: the dialogue option row sits past the bottom edge and gets clipped. Set 1280x800 and retest.  This also reframes the whole approach. The save file is a far better observation channel than memory: it is a documented, offline, structured snapshot containing party records (positions), gold, date, and global variables - no scanning, no injection, no focus games. Reading it gets us structured state (A) without touching the running process at all.   === ﻿feat: read structured game state from the save file, no process and no input === The first channel that works end to end, and it sidesteps all three blockers: memory scanning needs a running process, injected input is rejected by the engine's DirectInput path, and an unfocused window auto-pauses. The save file needs none of that.  Format, from sg00.sav cross-checked against the vendored editor sources:      +0x00  'WRDR'              magic     +0x04  uint32 0x3F3        1011, the game's own version, self-identifying     +0x0C  uint32 len + bytes  the player name, length-prefixed  Party map positions are x,y float pairs in the campaign range +-105, and every party stores its position several times with an 8-byte stride. That redundancy is what makes them findable: a raw scan yields about 750 candidates, but only 57 form stride-8 clusters of three or more. Repeated defaults such as 1.0/1.0 and 10.0/1.0 appear 25 and 91 times and are filtered as scale and rotation noise.  tools/save_state.py prints the header, the player and the 57 party records; --json emits them for an agent to consume. Verified against the user's real save.  For the A+B design this changes the plan: structured state does not require touching the running game at all. Observation can come from the save, and only actions still need a channel.   === ﻿feat: read each party's troop composition from the save as well === Position alone is not enough to decide anything. A party record turns out to be fully readable, so save_state.py --composition now reports, for all 57 parties: map position, facing, stack count, total men, and the troop-id/count pairs.  Layout, measured around a known record whose position sits at record + 0x00:      +0x18  float  facing / rotation     +0x1C  int    stack count     +0x20  int troop_id   +0x24 int count   +0x28 0   +0x2C 0     +0x30  ...next stack, 16 bytes apart  The two trailing zero ints in every 16-byte slot are what make the pattern recognisable.  Sample output against the real save:      ( -1.550,  66.450)  facing 0.5400   8 stacks  304 men   73x51 72x9 79x57 ...     (-22.750, -31.200)  facing 0.6976  16 stacks  121 men   86x5 91x9 90x4 87x22 ...  Parties that show 0 stacks are the transposed duplicates of a position (x,y stored again as y,x) rather than distinct parties - worth filtering in a later pass.  Still unfound: gold and the date. Both are best located by differential saves - change the value in game, save twice, diff - rather than by guessing. The live process already exposes gold at block + 0x3D8, so that one can be correlated directly.   === ﻿feat: the action half - edit the save instead of injecting input === The observation half landed in the previous commit. This is the other half, and it takes the opposite approach to everything tried before: rather than pushing events into a running game that reads its input through DirectInput and pauses when unfocused, write the state directly into the save file. The next load simply makes it true.      tools/save_state.py   read   -> 57 parties: position, facing, stacks, men     tools/save_edit.py    write  -> move a party, verified by reading it back  Verified end to end on a copy of the real save:      party 13  (-22.7500, -31.2000) -> (12.5000, -3.2500)     write 0x04E230 / 0x04E238 / 0x04E240     (all three position copies)     read back (12.5000, -3.2500)  ok=True     user's live save sha256 unchanged  Safety is part of the design rather than an afterthought: every write takes a timestamped backup first and refuses to proceed if the backup cannot be created, and --dry-run prints the exact byte ranges before anything is touched.  What this buys and what it costs. It rules out twitch combat - a save/reload cycle is not a realtime loop. It covers everything strategic, which in Mount & Blade is most of the game: moving the party, recruiting, trading, adjusting relations, positioning before a battle. And unlike injection it is deterministic: the write either verified or it did not.  Gold and the date are the next fields to locate. Both are best found by differential saves - change the value in game, save twice, diff for the changing int32 - since the live process already exposes gold at block + 0x3D8 to correlate against.   === ﻿feat: hardware input bridge - firmware and host driver, ready for the board === Software input is a dead end against this engine, and that conclusion is now backed by evidence rather than suspicion. Two channels were tried against a live game and both produced byte-identical frames before and after the click:      SendInput    synthetic events carry an injected flag; DirectInput reads device state                  and ignores them     PostMessage  never reaches the device at all - the engine does not read its message queue  DirectInput device state is only populated by an actual device. So: an Arduino Pro Micro acting as a real USB mouse and keyboard.      hardware/hid_bridge/hid_bridge.ino   firmware: serial commands -> HID events     hardware/hid_input.py                host driver: absolute moves, clicks, keys  Two design decisions worth recording.  Relative movement is kept deliberately. The Arduino Mouse library has no absolute mode, which normally forces a custom HID descriptor; instead the host closes the loop - send a delta, read the real cursor with GetCursorPos, send a correction. Two passes land within a pixel, and the position is verified rather than assumed. Relative movement also happens to be what DirectInput wants, so this is not even a compromise.  Click hold is 12 ms in the firmware, not zero. The engine samples the mouse once per frame, so a press and release inside one frame is invisible - the same lesson as the software path, which needed 70 ms; the hardware path needs less because the events arrive as real device reports.  Nothing here can be tested until the board arrives. What can be tested has been: the Python side compiles and enumerates ports, and the firmware is written against the documented Arduino Mouse and Keyboard APIs.   === ﻿fix: the occlusion that made every screenshot lie, plus wheel and paging keys === Three additions, all driven by failures observed while actually trying to play.  1. screen_capture.py - blit from the screen DC, not the window DC  The bridge's screenshot() blits the window's own DC. That rect is resolved against the screen, so it returns whatever is on top of the window there - including our own host window. Sampling single pixels settled it:      screen (750,300)  = RGB(21,21,23)     dark grey  - the DSH window     screen (1100,400) = RGB(143,112,70)   parchment  - the game     foreground        = the DSH window, not the game  So the left half of the character sheet had been coming back as blank parchment not because the game failed to draw it, but because the host window was sitting on top of it. The same occlusion swallowed clicks: the cursor was over the host window, which correctly took them.  Capturing from GetDC(NULL) with CAPTUREBLT reads the composited desktop instead, and moving the host window aside plus raising the game to the foreground gives a clean frame. Keeping the game window parked at a fixed position makes the coordinate table stable across restarts too, which removes a whole class of drift.  2. firmware: wheel support  Character creation extends past the bottom of the window and has no keyboard paging, so the attributes and weapon proficiencies were unreachable. Adds 'r <delta>' -> Mouse.move(0,0,d), chunked to the signed-byte limit. +98 bytes of flash.  3. hid_input: PageUp/PageDown/Home/End usage ids  The paging keys were unmapped and raised on first use. They did not end up paging this particular screen, but the mapping gap was real.  Also raises CLICK_HOLD_MS for the hardware path to 70 ms, matching what the software path needed: the engine samples the mouse once per frame, and a shorter press can fall inside a single frame and be invisible.   === ﻿feat: rewire the plugin onto the channels that actually work === The four tools shipped earlier were wired to the software input path - SendInput - which this engine ignores, and to a window-DC screenshot that the host window was sitting on top of. In practice that meant the plugin could report state and take pictures, and could not click. This replaces the internals.  New entry point: mb_agent.py  One CLI that owns all the behaviour, so the plugin stays thin and everything is testable from a terminal without involving DSH. Every command prints a single JSON object.      state                                   window, pid, gold, client rect, render scale     look [--scale N] [--out PATH]           screenshot from the composited screen     click X Y [--button left|right]         hardware click at a RENDER-space coordinate     key VK / wheel N / focus                hardware key, wheel, raise-and-unpause     save-state / save-parties / save-move    structured state and the working action channel  Three fixes baked into every command:    * Input goes through the USB HID device, not SendInput. DirectInput reads device state and     ignores injected events; a real mouse is not distinguishable from a human's.   * Coordinates are render-space. The engine renders 1280x800 into an 853x533 client and     scales pointer input by 1.5006, so a raw client coordinate lands about 50% too low. The     server divides; callers think in render pixels.   * The host window is moved aside and the game raised before any interaction. It used to sit     over the game, which made screenshots show the host and made clicks be eaten by it.  Plugin: 6 tools      mb_state       running, pid, client, render scale, gold     mb_look        screenshot, and the image->render mapping spelled out     mb_click       HID click, render-space coordinates     mb_key         HID key tap     mb_save_state  every party with position, facing, stacks and men - no game needed     mb_save_move   move a party in the save, backed up and verified  Verified without the game: state fails cleanly when nothing is running; save-state reads WRDR/1011/HYF and 41 parties; save-parties lists offsets; save-move --dry-run previews the byte change. The input paths still need a running game to re-verify.   === ﻿docs: rewrite the README around what works and where this stopped === The previous README oversold the project. It presented the 70 ms click hold as the fix for input, when the actual finding is that the engine ignores synthetic events entirely and only a physical USB HID device gets through - and it described the module-variable memory route as working, which it never did.  The replacement leads with an honest status line (on hold, ~40%), then a capability table where every row is marked by what was actually verified rather than what was attempted:      works      save read/write, hardware cursor to 1 px, click/key/wheel, screenshots,                gold from memory     does not   clicking anything in a menu or dialogue     not built  any ability to understand a screen  Three bugs each cost an evening and are now written up, because they are the reason the project is at 40% rather than 90%: the 1.5x render scale on pointer coordinates, the host window sitting on top of the game and poisoning both screenshots and clicks, and a menu with no hover feedback that makes coordinate guessing unable to converge.  "Where this stopped" says the real thing plainly: the plumbing was worth the time, the perception approach was not, and the fix is a vision model rather than more sweeping. It also lists what is unfinished so nobody assumes more than is there - including that verify_mailbox.py is inconclusive rather than passing.  Also documents the save format as measured, and the party-record layout.   === ﻿docs: Chinese status note, linked from the README === The audience for this project is largely Chinese-speaking, and the README is English.
