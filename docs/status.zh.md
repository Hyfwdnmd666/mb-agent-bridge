## 输入这一关为什么难，以及什么真正解决了它

**引擎通过 DirectInput 读取指针设备状态**，而它读的是*设备*状态，**忽略一切合成事件**。两条用户态通道都实测失败，判据是点击前后画面逐字节相同：

```
SendInput      合成事件带"注入"标记，DirectInput 直接忽略
PostMessage    根本到不了设备层，引擎不读自己的消息队列
```

解法不是更聪明的 API 调用，而是**一块独立的物理 USB 设备**：Arduino Pro Micro（ATmega32u4），跑 `hardware/hid_bridge/` 里的固件，对系统来说就是**一个真实的 USB 鼠标和键盘**。主机通过串口发文本指令，设备发出真正的 HID 报文。**在协议层面它就是鼠标，没有东西可供识别。**

两个关键设计：

- **故意保留相对移动。** Arduino 鼠标库没有绝对模式，通常必须写自定义 HID 描述符。这里改用闭环：发一个位移 → 用 `GetCursorPos` 读真实光标 → 发修正值。两轮就能落到 1 像素内，而且位置是**验证过的**，不是假设的。相对位移本来也正是 DirectInput 想要的，所以这甚至不算妥协。
- **点击按住 70ms。** 引擎逐帧采样，按下和抬起挤在一帧里就等于不存在。这个数字是**录下真人的点击**测出来的——每一次都按住约 70ms，且全是单击。

## 三个各花掉一晚上的 bug

项目停在 40% 而不是 90%，主要就是这三个。

### 1. 坐标要除以 1.5

引擎内部按 **1280x800** 渲染，而客户区是 **853x533**，指针坐标被缩放 `1280/853 = 1.5006`。**所有按客户区原始坐标发起的点击都偏低约 50%**，要么点空、要么点到别的东西上。

发现方式：请玩家把光标悬停在目标上，我读 `GetCursorPos` —— 光标在客户区 `y=240`，游戏却高亮了 `y≈352` 的行，而 `240 × 1.5 = 360`。

### 2. 我自己的窗口压在游戏上面

截图是从游戏窗口 DC 抓的。**那个矩形是按屏幕坐标解析的，所以返回的是"该位置最上层的画面"——包括宿主程序自己的窗口。** 单像素采样定的案：

```
屏幕 (750,300)  = RGB(21,21,23)     深灰   ← 宿主窗口
屏幕 (1100,400) = RGB(143,112,70)   羊皮纸 ← 游戏
```

所以角色表左半边一直是空白，**不是游戏没画，是宿主窗口盖住了**。同一个遮挡也吃掉了点击——光标下面是宿主窗口，它理所当然地接收了点击。

修法：改用 `GetDC(NULL)` + `CAPTUREBLT` 抓合成桌面，并把宿主窗口挪开、游戏窗口固定位置并置顶。

### 3. 主菜单没有悬停反馈，所以"猜坐标"永远不收敛

菜单是静态图，**点错了没有任何可见信号**，无法区分"坐标不对"和"输入被拒"。游戏唯一可靠的信号是：**点一下，看画面变没变。**

第一次扫描之所以无效，是因为它从不校验自己在哪里：某一步点开了新游戏开场文本，`ESC` 退不出来，**后面连续 11 个采样测的都是同一个卡住的界面**。

## 停在哪里，为什么

**停在感知层，而感知恰恰是全部问题所在。**

所有"能行动"的东西都已经建好并验证过。**不存在的是任何"看懂屏幕"的能力** —— 没有目标检测、没有 OCR、没有 UI 模型，坐标是逐个界面手工扫描出来的。**这对一个有几百个界面的游戏不可扩展**，也正是为什么一个按钮能耗掉一整个晚上。

**诚实的总结：** 时间花在了管道上——输入传输、坐标系统、窗口层叠、存档格式——**而这些恰恰是同类项目最容易死掉的地方，它们确实通了**。但我在感知上用的是 1990 年代的办法：手量像素、网格扫描。**这个年代的正确解法是视觉模型：**

```python
frame  = look()                                            # 现在就能用
target = vision_model(frame, "完成按钮在哪里？")             # ← 缺的就是这一行
click(target)                                              # 现在就能用
```

**底层基础设施正是视觉驱动型 agent 需要的东西，一行都不用改。缺的那块在别处是已解决的问题。** 这是下一步，也是我选择停在这里、而不是继续磨坐标的原因。
